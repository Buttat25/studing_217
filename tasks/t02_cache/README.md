# Задача 2. Кэш для быстрого справочника

Напишите быстрый справочник, который хранит много пар «ключ — значение» (артикул — товар).
Пользователь запрашивает значение по ключу — программа мгновенно его возвращает. Если значения
нет — программа «идёт искать» (долгий запрос, например 1 секунда) и сохраняет результат, чтобы
в следующий раз отдать сразу. Кэш ограничен: при переполнении удаляются давно не использованные записи.

**Что нужно продумать:**
- как превратить строку-ключ в номер ячейки, чтобы поиск был мгновенным даже при тысячах записей;
- что делать при коллизии: список в ячейке (цепочки) или поиск следующей свободной (открытая адресация);
- какие записи удалять первыми и как при удалении не сломать поиск других записей;
- как проверить, что справочник действительно быстрый (10, 1000, 100 000 записей);
- пустой кэш, полностью заполненный, несуществующий ключ, повторное добавление ключа.

## Программа
Создайте в папке задачи файл `cache.py`. Тесты запускают его как программу и проверяют только
ввод и вывод — как устроен код внутри, решаете вы.

**Запуск:** `python cache.py КАТАЛОГ [--size N] [--delay СЕК]`
- `КАТАЛОГ` — файл «внешнего источника» (UTF-8, BOM допустим): по строке `ключ; описание`
  (делит первая `;`, пробелы по краям убираются). Пустые строки и строки с `#` в начале пропускаются.
- `--size N` — лимит кэша, целое число больше 0 (по умолчанию 1000).
- `--delay СЕК` — сколько секунд «думает» источник при каждом обращении (по умолчанию 0;
  `--delay 1` — как в условии). Параметры можно указывать в любом порядке.

**Команды** читаются из стандартного ввода, по одной в строке (пустые строки пропускаются).
Команды пишутся строчными буквами; ключ — всё после команды, без пробелов по краям
(внутри ключа пробелы и любые символы допустимы, кроме `;` в `put`).

| Команда | Ответ |
|---|---|
| `get КЛЮЧ` | `КЛЮЧ: "описание" [из кэша]`, `КЛЮЧ: "описание" [из внешнего источника]` или `КЛЮЧ: [товар не найден]` |
| `put КЛЮЧ; ЗНАЧЕНИЕ` | `КЛЮЧ: сохранено` — записать или обновить значение прямо в кэше, без источника |
| `del КЛЮЧ` | `КЛЮЧ: удалено из кэша` или `КЛЮЧ: нет в кэше` |
| `list` | `Кэш (3 из 1 000): K3, K1, K2` — ключи от самого свежего к самому давнему; пустой — `Кэш (0 из 1 000): пусто` |
| `stats` | блок статистики (см. пример) |

Неверная команда (неизвестная, пустой ключ, `put` без значения) — строка `ОШИБКА: <описание>`,
программа продолжает работу. Числа от 1000 печатаются с пробелом между разрядами: `12 345`.
Доля попаданий — с одним знаком после точки (`33.3%`, при 0 запросов — `0.0%`).

**Ошибки запуска:** неверные аргументы (нет каталога, `--size 0`, `--delay -1`, лишний аргумент) —
`Ошибка: <описание>` в stderr и код 2. Нет файла каталога или ошибка в нём (строка без `;`,
пустой ключ или описание, повтор ключа) — `Ошибка: …` с номером строки и код 1.
Программа не должна падать с трассировкой (Traceback).

## Договорённости (их проверяют тесты)
- Кэш хранит не больше `--size` записей; при переполнении вытесняется **самая давно
  использованная** запись (LRU). Использование — это `get` (попадание или загрузка из источника) и `put`.
- Ненайденное **не кэшируется**: повторный запрос снова идёт в источник.
- `put` существующего ключа обновляет значение без дубликата, запись становится самой свежей.
- Ключи, похожие друг на друга (`ab` и `ba`, `SKU-12` и `SKU-21`), — разные ключи.
- 100 000 запросов при лимите 100 обрабатываются за секунды.

**Требования к коду (проверяются автоматически по исходникам, `check.py` покажет нарушения):**
хэш-таблица и список «давности» — **свои**. Во всех файлах решения задачи нельзя пользоваться
встроенными словарями и множествами: `dict`, `set`, `frozenset`, литералы `{…}` (словари и
множества), `collections.OrderedDict`/`defaultdict`/`Counter`/`ChainMap`, `functools.lru_cache`/`cache`.
Каталог тоже храните в своей хэш-таблице. Хэш-функция строки — своя и одинаковая между запусками
(встроенный `hash()` для строк меняется от запуска к запуску). Нарушение — минус баллы за задачу.

## Пример
Каталог `catalog.txt`:
```
SKU-1001; Смартфон X-Pro, 128 ГБ, чёрный
SKU-2045; Наушники беспроводные SoundMax
SKU-3300; Чехол для смартфона силиконовый
```
Команды (`python cache.py catalog.txt --delay 1 < commands.txt`):
```
get SKU-1001
get SKU-2045
get SKU-1001
get SKU-3300
get SKU-9999
get SKU-2045
stats
```
Вывод:
```
SKU-1001: "Смартфон X-Pro, 128 ГБ, чёрный" [из внешнего источника]
SKU-2045: "Наушники беспроводные SoundMax" [из внешнего источника]
SKU-1001: "Смартфон X-Pro, 128 ГБ, чёрный" [из кэша]
SKU-3300: "Чехол для смартфона силиконовый" [из внешнего источника]
SKU-9999: [товар не найден]
SKU-2045: "Наушники беспроводные SoundMax" [из кэша]
Статистика работы кэша:
  Всего запросов: 6
  Попаданий в кэш: 2 (33.3%)
  Промахов (обращений к внешнему источнику): 4
  Из них не найдено: 1
  Размер кэша: 3 из 1 000
  Вытеснено записей по стратегии LRU: 0
```

## Git-сценарий (параллельные эксперименты)
Всё делается в общем репозитории курса, в ваших ветках и тегах: вместо `<логин>` — ваша фамилия
латиницей в нижнем регистре (`ivanov`). Ваша «главная» ветка — `<логин>/main`; если её ещё нет,
создайте от `main`: `git switch -c <логин>/main main`. Ветки и теги отправляйте в репозиторий:
`git push origin <ветка> <тег>…`. Не удаляйте ветки, которые нужны для проверки.

1. Создайте ветку разработки: `git switch -c <логин>/develop main`.
2. От неё — две ветки экспериментов: `<логин>/experiment/chaining` (хэш-таблица с цепочками) и
   `<логин>/experiment/open-addressing` (открытая адресация). В каждой реализуйте свою стратегию
   и закоммитьте.
3. Замерьте скорость обеих на 10, 1000 и 100 000 записей (например, временем работы программы на
   большом каталоге) и запишите результаты и вывод в `tasks/t02_cache/EXPERIMENT.md`.
4. Лучшую ветку слейте в `<логин>/develop`. На вторую поставьте тег `<логин>-t02-rejected`
   (`git tag <логин>-t02-rejected <логин>/experiment/…`) — так её коммиты сохранятся — и удалите
   ветку: `git branch -D …`, а если она уже отправлена — `git push origin --delete …`.
5. Закоммитьте `EXPERIMENT.md` в `<логин>/develop`, отправьте ветки и тег.

Что проверяется: есть `<логин>/develop`; осталась ровно одна ветка эксперимента, и она влита в
develop; отклонённая сохранена тегом `<логин>-t02-rejected` и в develop не попала; оба эксперимента
начаты от develop; в develop есть `EXPERIMENT.md` с замерами обеих стратегий (числами) и выводом.
