# Задача 5. Анализатор дневника событий

Есть текстовый файл с событиями (время, тип, описание). Программа читает файл, находит ошибки,
группирует события по типу и строит отчёт: сколько было событий каждого типа, когда были пики
активности, были ли подозрительные промежутки без событий.


## Программа
Создайте в папке задачи программу `eventlog.py` (имя может быть другим - см. README курса).

**Запуск:** `python eventlog.py ФАЙЛ [--bucket МИН] [--gap МИН]`
- `--bucket` - длина интервала для пиков активности, целое число минут (по умолчанию 60); сутки
  должны делиться на него без остатка (1, 15, 30, 60, 90, 1440…).
- `--gap` - порог подозрительного промежутка, целое число минут (по умолчанию 30).

**Строка журнала:** `ГГГГ-ММ-ДД ЧЧ:ММ:СС <разд> ТИП [<разд> описание]`
- Разделитель - `|`, `;` или табуляция, **один и тот же** в строке; пробелы вокруг разделителей
  и по краям строки допустимы. Между датой и временем - один пробел или `T`.
- `ТИП` - латинская буква, затем латинские буквы, цифры или `_`; приводится к верхнему регистру.
- После секунд может стоять часовой пояс: `Z`, `+03:00`, `-0500` (часы ≤ 14, минуты ≤ 59). Такое
  время переводится в UTC, время без пояса считается уже заданным в UTC.
- В описании могут быть поля `ключ=значение` через запятую (значение можно взять в кавычки):
  `code=503, msg="service unavailable"`.
- Любая другая строка - битая (неверный формат, несуществующая дата `2026-13-45`, `24:00:00`,
  нет типа). Пустые строки не считаются вовсе.

**Вывод**:
- Заголовок - `Отчёт по файлу <имя файла без папок>:`; размер файла - `616 Б`, `1.5 КБ` или
  `5.0 МБ` (1 КБ = 1024 Б, один знак после точки); `Всего строк` - непустые строки.
- `Битых строк: 0`, а если они есть - `Битых строк: 1 (пропущены)`. Если события записаны не по
  порядку, следом строка `  Записано не по порядку времени: N` (N - сколько событий оказались
  раньше уже встреченного максимума времени).
- Если есть битые строки - раздел `Примеры битых строк:` с первыми десятью: `  строка 7: <текст>`
  (номер - по всем строкам файла, включая пустые).
- Типы - в порядке первого появления; имя дополняется пробелами до длины самого длинного + 2,
  количество выравнивается вправо; доля - от разобранных событий, один знак после точки.
- Время в отчёте - `ЧЧ:ММ:СС` (интервалы - `ЧЧ:ММ–ЧЧ:ММ`); если события приходятся на разные
  даты - с датой: `2026-11-05 23:50:00`, `2026-11-05 22:00–00:00`.
- Числа от 1000 - с пробелом между разрядами; слова - `1 событие`, `2 события`, `5 событий`,
  `1 ошибка`, `3 ошибки`, `5 ошибок`. Пустые разделы - `нет событий`, `нет данных`, `не обнаружено`.

## Договорённости
- Повторяющиеся события считаются отдельно.
- Пики - по интервалам `--bucket` от полуночи; пустые интервалы между первым и последним событием
  тоже учитываются; при равенстве - самый ранний. Среднее - разобранные события / число интервалов.
- Подозрительный промежуток - событие позже предыдущего **максимума** времени **больше** чем на
  `--gap` минут; длительность - в целых минутах (с отбрасыванием). События не по порядку не
  создают ложных промежутков.
- Серия ошибок - 3 и больше события `ERROR` подряд (битые строки серию не прерывают, события
  других типов - прерывают). В строке серии - время первой и последней ошибки и коды из поля
  `code` (без повторов, по алфавиту).
- Файл читается **потоком** (по строке): события не складываются в список, память не растёт вместе
  с размером файла. Файл в UTF-8; неверные байты заменяются символом `�`, а строка
  разбирается как обычно.

## Git-сценарий (поиск ошибки в истории)
Задание выполняется **в этом же репозитории**, в папке `git_practice/t05_grades/`. Там лежит
учебная программа «Сводка оценок» (не связана с решением этой задачи). Когда её добавили, все тесты
проходили (коммит с тегом `t05-start`), а в `main` тесты падают. В одном из коммитов спрятана
ошибка. Историю `main` переписывать нельзя: вся работа - в **вашей ветке**, а результат
помечается **вашими тегами**.

Вместо `<логин>` - ваш логин в edu.susu.

1. Создайте свою ветку от `main`:
   ```bash
   git switch -c <логин>/t05 main
   ```
2. Найдите коммит с ошибкой автоматически:
   ```bash
   git bisect start main t05-start
   git bisect run python -m pytest -q git_practice/t05_grades
   git bisect log > bisect_log.txt
   git bisect reset
   ```
   `git bisect reset` обязателен: до него вы не на своей ветке, и коммиты уйдут «в никуда».
3. Поставьте тег на найденный коммит: `git tag <логин>-t05-bug <sha>`.
4. Откатите этот коммит в своей ветке: `git revert <sha>`. Не используйте `reset` и `rebase`:
   историю переписывать нельзя. Поставьте тег на коммит отката: `git tag <логин>-t05-fix`.
5. По желанию перенесите журнал поиска в `git_practice/t05_grades/bisect_log.txt` и закоммитьте
   его отдельным коммитом.
6. Убедитесь, что тесты проходят (`python -m pytest -q git_practice/t05_grades`). Отправьте ветку
   и теги туда, куда скажет преподаватель:
   ```bash
   git push origin <логин>/t05 <логин>-t05-bug <логин>-t05-fix
   ```

Что проверяется:
- ветка `<логин>/t05` создана от `main`, исходная история на месте;
- тег `<логин>-t05-bug` стоит на ошибочном коммите;
- тег `<логин>-t05-fix` стоит на коммите отката в вашей ветке;
- откачен именно ошибочный коммит и только он, других изменений в программе нет;
- тесты проходят.

Журнал `git bisect` и хеш ошибочного коммита в сообщении отката (`git revert` добавляет его сам)
дают дополнительный плюс.
