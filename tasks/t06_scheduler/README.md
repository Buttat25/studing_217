# Задача 6. Планировщик задач с зависимостями

Программа управляет списком задач, где одни задачи зависят от других («собрать проект» зависит от
«написать код», «выкатить на продакшн» - от «собрать проект» и «прогнать тесты»). Она показывает,
какие задачи можно выполнить прямо сейчас, в каком порядке выполнять все задачи, и ругается на
циклические зависимости.

## Программа
Создайте в папке задачи программу `scheduler.py` (имя может быть другим - см. README курса). Два режима:

### 1. План по списку задач: `python scheduler.py tasks.txt`
Файл (UTF-8) - по строке на задачу:
```
Задача C: "Собрать проект" - зависит от: A, B
```
- Имя задачи - одно «слово» без пробелов (любые символы, кроме пробелов и запятых), пустым быть
  не может; название - в кавычках (может быть пустым `""`); перед «зависит от:» - дефис `-`;
  слова «Задача» и «зависит от:» - в любом регистре; лишние пробелы допустимы.
- Нет зависимостей - `-` или пусто; повтор зависимости не считается. Задача может зависеть
  от той, что описана ниже. Пустые строки и строки с `#` в начале пропускаются.

**Вывод** (stdout, код 0) - как в примере ниже. Если название пустое, задача печатается просто
именем (`2. B`). Пустые разделы - `  нет` (готовые) и `  нет задач` (порядок, этапы).

**Цикл** - в stdout ровно три строки и код 1:
```
ОШИБКА: обнаружена циклическая зависимость!
Цепочка: X → Y → Z → X
Невозможно определить порядок выполнения.
```
Цепочка - любой цикл из графа: каждая задача зависит от следующей, первая повторяется в конце
(зависимость от самой себя - `X → X`).

### 2. Диалог: `python scheduler.py < commands.txt`
Без аргументов программа читает команды из стандартного ввода, по одной в строке (пустые строки
пропускаются); слова разделяются пробелами, команды - строчными буквами.

| Команда | Ответ |
|---|---|
| `add ИМЯ [ЗАВ1 ЗАВ2 …]` | `Задача ИМЯ добавлена` (с зависимостями; при ошибке не добавляется ничего) |
| `dep ИМЯ ОТ_ЧЕГО` | `ИМЯ зависит от ОТ_ЧЕГО` (повторно - тот же ответ) |
| `undep ИМЯ ОТ_ЧЕГО` | `ИМЯ больше не зависит от ОТ_ЧЕГО` |
| `remove ИМЯ [--force]` | `Задача ИМЯ удалена`; без `--force` нельзя удалить задачу, от которой зависят другие (в ошибке - их имена); с `--force` удаляются и ссылки на неё |
| `done ИМЯ` | `Задача ИМЯ выполнена` - только ожидающую задачу, все зависимости которой выполнены |
| `fail ИМЯ` | `Задача ИМЯ провалена` или `…провалена; заблокированы: C, D` - только ожидающую (не заблокированную) |
| `reset ИМЯ` | `Задача ИМЯ снова ожидает` или `…; разблокированы: C` - только проваленную |
| `status ИМЯ` | `ИМЯ: ожидает` / `выполнена` / `провалена` / `заблокирована` |
| `ready` | `Готовы к выполнению: A, D` или `Готовы к выполнению: нет` |
| `order` | `Порядок: A, B, C` или `Порядок: нет задач` |
| `stages` | строки `Этап 1: [A, E]`; без задач - `нет задач` |
| `plan` | тот же план, что в режиме 1 |
| `deadline ИМЯ ГГГГ-ММ-ДД` | `Задача ИМЯ: дедлайн 2026-11-10` - задача становится задачей с дедлайном (повторно - дедлайн меняется) |
| `overdue ГГГГ-ММ-ДД` | `Просрочены: A, C` или `Просрочены: нет` - невыполненные задачи с дедлайном раньше этой даты (по алфавиту) |
| `save ФАЙЛ` | `Сохранено в ФАЙЛ` - всё состояние (задачи, названия, зависимости, статусы, дедлайны) в файл JSON |
| `load ФАЙЛ` | `Загружено задач: 3` - состояние полностью заменяется сохранённым |

Любая ошибка - строка `ОШИБКА: <описание>`, граф и статусы не меняются, работа продолжается.
Попытка создать цикл (`dep`, `add`) - ошибка с цепочкой от задачи, к которой добавляли
зависимость, до неё же: при `B → A` команда `dep A B` даёт `ОШИБКА: циклическая зависимость: A → B → A`.

## Договорённости
- Порядок однозначен: из доступных задач первой идёт задача с наименьшим именем (сравнение строк).
- Этап задачи - 1 + наибольший этап её зависимостей; внутри этапа задачи по алфавиту.
- «Готовы» - ожидающие задачи, все зависимости которых выполнены (по алфавиту).
- «Заблокирована» - вычисляемый статус ожидающей задачи, у которой провалена какая-то зависимость
  (прямая или через цепочку). `fail` сообщает, какие задачи стали заблокированными, `reset` - какие
  перестали (по алфавиту).
- Работает на цепочке из 20 000 задач (без рекурсии - Python ограничивает её глубину) и на тысячах
  задач, зависящих от одной.
- Файл `save` - корректный JSON (структуру выбираете сами); `load` восстанавливает всё, в том числе
  в новом запуске программы.
- Дата - в формате `ГГГГ-ММ-ДД`. Удалённая задача теряет и дедлайн.

## Пример
```
Задача A: "Написать код"           - зависит от: -
Задача B: "Написать тесты"         - зависит от: A
Задача C: "Собрать проект"         - зависит от: A, B
Задача D: "Прогнать тесты"         - зависит от: C
Задача E: "Выкатить на продакшн"   - зависит от: C, D
Задача F: "Обновить документацию"  - зависит от: E
```
```
Проверка зависимостей: циклов не обнаружено.

Задачи, готовые к выполнению прямо сейчас:
  ✓ A: "Написать код"

Порядок выполнения всех задач (топологическая сортировка):
  1. A: "Написать код"
  2. B: "Написать тесты"
  3. C: "Собрать проект"
  4. D: "Прогнать тесты"
  5. E: "Выкатить на продакшн"
  6. F: "Обновить документацию"

Параллельные потоки (что можно делать одновременно):
  Этап 1: [A]
  Этап 2: [B]
  Этап 3: [C]
  Этап 4: [D]
  Этап 5: [E]
  Этап 6: [F]
```

## Git-сценарий (поиск автора строки и исправление в чужом коде)
Задание выполняется **в этом же репозитории**, в папке `git_practice/t06_library/`. Там лежит
учебная программа «Библиотека» (не связана с решением этой задачи). Тесты в `main` проходят, но
три теста пропускаются (`SKIPPED`). Их «временно» отключили в тех же коммитах, где в код попали
ошибки. Тестировщики описали симптомы ошибок в `git_practice/t06_library/ISSUES.md`.
Свои тесты писать не нужно: готовые отключённые тесты как раз ловят эти ошибки.

Историю `main` переписывать нельзя: вся работа - в **вашей ветке**, а результат помечается
**вашими тегами**. Вместо `<логин>` - ваш логин в edu.susu.

1. Создайте свою ветку от `main`:
   ```bash
   git switch -c <логин>/t06 main
   ```
2. Для **каждой** ошибки из `ISSUES.md` (по порядку номеров):
   1. Найдите проблемную строку и коммит, в котором она появилась:
      `git blame git_practice/t06_library/library.py` (или с `-L <начало>,<конец>`), затем
      `git show <sha>` - посмотрите, что ещё поменялось в том коммите.
   2. Исправьте ошибку и включите отключённый в том коммите тест (уберите строку
      `@pytest.mark.skip(...)`). Убедитесь, что все тесты проходят:
      `python -m pytest -q git_practice/t06_library`.
   3. Закоммитьте исправление **отдельным коммитом**. В теле сообщения укажите виновный коммит:
      ```
      fix(t06): штраф начислялся на день раньше срока

      Ошибка внесена в 1a2b3c4d.
      ```
   4. Поставьте тег с номером ошибки из `ISSUES.md`: `git tag <логин>-t06-fix-<номер>`.
3. Отправьте ветку и теги туда, куда скажет преподаватель:
   ```bash
   git push origin <логин>/t06 <логин>-t06-fix-1 <логин>-t06-fix-2 <логин>-t06-fix-3
   ```

Что проверяется:
- ветка `<логин>/t06` создана от `main`, исходная история на месте;
- изменения только в `git_practice/t06_library/`;
- в конце ветки все тесты включены и проходят;
- для каждой ошибки есть тег `<логин>-t06-fix-<номер>` на коммите вашей ветки, который исправляет
  ровно эту ошибку;
- в сообщении этого коммита указан хеш виновного коммита.
