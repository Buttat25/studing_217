## Установка
Нужны Python 3.10+ и git.
```bash
python -m venv .venv
```
Активируйте окружение - Windows: `.venv\Scripts\activate`, macOS/Linux: `source .venv/bin/activate`.
```bash
python -m pip install -r requirements.txt
```

## Как устроена задача
```
tasks/tNN_name/
├── README.md        ← условие, формат ввода и вывода программы, договорённости, пример, git-сценарий
└── tests/           ← готовые тесты (не изменяйте их)
```

Имя файла из README - рекомендуемое. Программу можно назвать иначе (например, `main.py`): если
файла с именем из README нет, тесты запускают единственный `.py`-файл в папке задачи, а если файлов
несколько - тот, в котором есть `if __name__ == "__main__":` (такой файл должен быть один).

Тесты запускают программу, подают ей ввод (файл, аргументы, строки на стандартный ввод) и
сравнивают её вывод с ожидаемым строка в строку (пробелы в конце строк не важны), поэтому формат
вывода из README нужно соблюдать точно. Открытые тесты - в `tests/`.

## Ошибки во входных данных
Какие входные данные считать ошибочными - часть задания: такие случаи нужно найти самим.
Сообщать об ошибке нужно так (это проверяют тесты):
- программа, которая читает файл, аргументы или стандартный ввод и печатает отчёт (задачи 1, 4, 5,
  режим «файл» задачи 6, а также файл каталога или зала в задачах 2 и 3), печатает в stderr строку
  `Ошибка: <описание>` и завершается с кодом 1, отчёт не печатается; неверные аргументы
  командной строки - та же строка и код 2;
- в диалоге (команды задач 2, 3, 6 и 7) - строка `ОШИБКА: <описание>` в stdout, состояние
  не меняется, программа продолжает работу;
- в описании назовите, что именно не так: неверное значение, номер строки входного файла
  (`строка 3`), имя поезда, задачи или файла;
- программа не должна падать с трассировкой (Traceback).

## Как запускать тесты
Все команды выполняются **из корня репозитория** (папки, где лежит этот README) с активированным
окружением: в начале строки терминала должно быть `(.venv)`. Активировать окружение:
- Windows, cmd: `.venv\Scripts\activate`
- Windows, PowerShell: `.venv\Scripts\Activate.ps1` (если PowerShell запрещает запуск скриптов,
  один раз выполните `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`)
- macOS/Linux: `source .venv/bin/activate`

Без активации можно вызывать Python окружения напрямую: `.venv\Scripts\python tools/check.py 1`
(Windows) или `.venv/bin/python tools/check.py 1` (macOS/Linux).

### Шаг 1. Создайте программу
Положите программу **прямо в папку задачи** (не во вложенную папку), например
`tasks/t01_trains/trains.py`.

В задаче 7 модули `calc_math.py`, `calc_convert.py`, `calc_matrix.py`, `calc_logic.py` называются
строго так, а главную программу можно назвать как угодно (по правилам выше).

### Шаг 2. Запустите проверку - `tools/check.py`
Одна задача (номер или имя папки):
```bash
python tools/check.py 1
```
```bash
python tools/check.py t01_trains
```
Все задачи сразу (в конце - сводная таблица):
```bash
python tools/check.py all
```
Подробно - какие тесты упали, что ожидалось и что напечатала ваша программа:
```bash
python tools/check.py 1 -v
```

Результат выводится по категориям тест-кейсов:
<!-- пример отчёта: начало -->
```
Задача 1:
- Типичные: 14/14 ✓
- Наивные: 11/11 ✓
- Краевые: 18/18 ✓
- Формат: 41/41 ✓
- Фаззинг: 9/9 ✓
Итого: 93/93
```
<!-- пример отчёта: конец -->

Сообщения `check.py`:
- `Нет файла: trains.py` - в папке задачи нет ни одного `.py`-файла;
- `Не найдена программа trains.py: в папке несколько файлов (…)` - непонятно, какой файл запускать
  (см. шаг 1);
- `Тесты: превышено время` - где-то бесконечный цикл, очень медленный алгоритм или программа ждёт
  ввода, которого не будет.

### Шаг 3. Разберитесь с упавшими тестами
В подробном режиме (`-v`) для каждого упавшего теста показано, в чём расхождение:
```
Вывод не совпадает (- ожидается, + ваш вывод):
-Минимальное количество платформ: 2
+Минимальное количество платформ: 5
код возврата 0
```
Строки с `-` - то, что должна была напечатать программа, с `+` - то, что напечатала ваша. Ниже -
код возврата и то, что программа вывела в stderr (там же будет трассировка, если программа упала).
`…` в ожидаемой строке означает «любой текст».

Другие виды сообщений:
- `ожидался код возврата 1` - программа завершилась не с тем кодом (`sys.exit(1)` при ошибке
  в данных, `2` - при неверных аргументах, если так сказано в README);
- `в stderr нет строки, начинающейся с «Ошибка:»` - сообщение об ошибке напечатано не туда
  (нужно `print("Ошибка: …", file=sys.stderr)`) или не в том виде;
- `в сообщении об ошибке нет: 'строка 3'` - в тексте ошибки не хватает обязательной детали
  (номера строки, имени и т. п. - см. README задачи);
- `программа упала с исключением` - трассировка (Traceback) вместо понятного сообщения;
- `В выводе нет строки '…'` - в выводе не нашлось нужной строки (проверяется только её наличие
  в нужном порядке).

Показываются первые 120 строк разбора: исправьте эти тесты и запустите проверку снова.

### Запустить тесты через pytest напрямую
Так удобно гонять один тест или останавливаться на первом падении (из корня репозитория).
Программа ищется по тем же правилам, что и в `check.py`.
```bash
python -m pytest tasks/t01_trains
```
```bash
python -m pytest tasks/t01_trains -x
```
```bash
python -m pytest tasks/t01_trains -k midnight
```
```bash
python -m pytest "tasks/t01_trains/tests/test_trains.py::test_example_from_stdin"
```
`-x` - остановиться на первом упавшем тесте, `-k слово` - только тесты, в имени которых есть это
слово, `--tb=short` - короче трассировки.
`python -m pytest` без аргументов запускает тесты всех задач.
Тесты git-заданий задач 5 и 6 запускаются так же:
`python -m pytest -q git_practice/t05_grades`.

Ещё тесты запускаются сами при каждом `git push` в GitHub (вкладка Actions, результат - в Summary).
Сборка не «краснеет» из-за недоделанных задач - смотрите таблицу в Summary.

### Частые проблемы
- **`No module named pytest`** - не активировано окружение или не установлены зависимости
  (`python -m pip install -r requirements.txt`).
- **`can't open file 'tools/check.py'`** - команда запущена не из корня репозитория.
- **«Нет файла» / «Не найдена программа»** - программа должна лежать прямо в папке задачи. Если
  в папке несколько `.py`-файлов, назовите программу как в README или оставьте
  `if __name__ == "__main__":` только в ней.
- **Превышено время / тест «завис»** - бесконечный цикл, очень медленный алгоритм или программа ждёт
  ввода с клавиатуры там, где должна читать файл из аргумента (или наоборот).
- **Лишний текст в выводе** (приглашения `> `, подсказки) - тесты сравнивают вывод строка в строку:
  печатайте только то, что сказано в README задачи.
- **Трассировка (Traceback) вместо «Ошибка: …»** - ошибку во входных данных нужно поймать
  (`try/except`) и сообщить о ней, как сказано в разделе «Ошибки во входных данных».
- **Тесты не изменяйте.**

## Сдача
```bash
python tools/check.py submit --name "Фамилия Имя"
```
Команда проверит все задачи и создаст архив `submissions/submission_<имя>_<дата>.zip` с вашими
решениями и отчётом по категориям (он же - рядом в файле `.txt`). Архив отправляется
преподавателю вместе с основным отчётом.

## Git-сценарии
У каждой задачи есть git-сценарий (описан в конце README задачи). Все они выполняются в этом же
репозитории и проверяются автоматически по веткам и тегам. Общая история в `main` у всех одна,
переписывать её нельзя. Каждый студент:
- работает только в **собственных ветках** с логином в начале: `<логин>/main` (ваша главная ветка,
  от `main`), `<логин>/t01-solution`, `<логин>/develop`, `<логин>/t05`, `<логин>/t06` и т. д.;
- помечает результат **собственными тегами**: `<логин>-t05-bug`, `<логин>-v1.0.0` и т. д.;
- отправляет ветки и теги в репозиторий (`git push origin <ветка> <теги>`).

`<логин>` - ваш логин в edu.susu. Ветки и теги чужих логинов не трогайте.
Задачи 5 и 6 выполняются на учебных программах из папки `git_practice/`:
- `git_practice/t05_grades/` - «Сводка оценок», поиск ошибки через `git bisect` и откат через `git revert`;
- `git_practice/t06_library/` - «Библиотека», поиск виновного коммита через `git blame` и исправление ошибок.
